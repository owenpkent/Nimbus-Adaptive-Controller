## 1. Why a driver, in one paragraph

On Linux, Nimbus takes the physical mouse away from the game with one `EVIOCGRAB` ioctl and draws its own cursor. On Windows the same outcome needs a kernel-mode filter, because user mode has no equivalent call. That is not a guess any more: `tests/probe_rawinput_windows.py` shows that a `WH_MOUSE_LL` hook that drops 100% of mouse events leaves `WM_INPUT` untouched, that the only user-mode action that stops `WM_INPUT` is taking the foreground away from the game, and `tests/probe_game_mouselook_windows.py` shows that Elden Ring stops reading the gamepad the moment it loses the foreground. Microsoft's HID architecture page states the reason: mouse and keyboard top-level collections are opened exclusively by the Raw Input Manager, so no process can read or block them from user mode.

## 2. What to build

A small KMDF upper filter on the mouse class (class GUID `{4D36E96F-E325-11CE-BFC1-08002BE10318}`), started from Microsoft's `moufiltr` sample, that does exactly two things:

1. **Pass-through by default.** With no client attached, every `MOUSE_INPUT_DATA` packet goes to `mouclass` unchanged. Installing the driver changes nothing for anyone.
2. **Isolation on request.** While a user-mode client holds the control device open and has switched isolation on, packets from the physical mice are **not** forwarded to `mouclass` (so neither the cursor nor Raw Input nor any game sees them) and are instead handed to the client.

Everything else happens in user mode: deadzones, curves and the virtual pad already exist, and what becomes of the cursor is the client's choice (section 2.2). On Windows that choice is the **cursor relay**: Nimbus moves the real cursor itself, so the mouse keeps working everywhere while the game, which keeps the foreground, never sees it.

### 2.1 Kernel side

| Item | Decision |
|---|---|
| Base | WDK `moufiltr` sample (KMDF). `MouFilter_ServiceCallback` is the one function that matters: it is where packets are dropped or forwarded. |
| Control device | `\\.\NimbusMouseFilter`, one client at a time. |
| Packet delivery | Inverted call: the client keeps a `ReadFile` pending on the control device; the driver completes it with an array of `MOUSE_INPUT_DATA` (verbatim: `UnitId`, `Flags`, `ButtonFlags`, `ButtonData`, `RawButtons`, `LastX`, `LastY`, `ExtraInformation`). If no read is pending, packets go to a bounded ring (drop oldest) so a slow client never stalls the input stack. A read issued or pending while isolation is off fails with `STATUS_DEVICE_NOT_READY`, which is how the client learns about a watchdog release (interface v2). |
| Control | `IOCTL_NIMBUS_SET_ISOLATION {enabled: ULONG}` and `IOCTL_NIMBUS_GET_STATUS` (version and counters). |
| Device selection | First version: all mice. Second version: per-`UnitId` mask, since combo devices and multi-node mice exist on Windows too. |
| Release guarantees | Isolation is tied to the client handle: `IRP_MJ_CLEANUP` (crash, kill, exit) restores pass-through. Plus a watchdog: if no read has arrived for 2 s while isolated, restore pass-through. Since interface v3 a read parked with nothing to deliver is completed empty after `NIMBUS_MOUFILTER_TICK_MS` (a heartbeat tick; 1 s on v3, 250 ms since v4) and only a read's arrival counts as life, so a client that is frozen or suspended, not just dead, loses the mouse within 2 s (on v2 a parked read kept isolation alive by design). The other side of that coin, measured in section 5 item 11: a live client survives a stall of 2 s minus the age of its parked read, which is re-issued after each tick. On v3 that floor was 0.75 s; v4's 250 ms tick keeps the read under about 0.5 s old, so it is 1.5 s. The client's reader thread runs at time-critical priority for the same reason. Keyboard is never touched, so `Ctrl+Alt+Del` always works, and the client polls `Ctrl+Alt+F12` itself (section 2.2). |
| Access control | The control device grants `GENERIC_READ` and `GENERIC_WRITE` to Interactive Users, because Nimbus runs unprivileged. Any interactive process can therefore hold the mouse, and a process in another session can suppress the console user's mouse, which no user-mode mechanism allows. Analysis, the rejected broker-service alternative, and what to change before the first shipped release are in [driver/README.md](../../driver/README.md), "Security model". |
| Injection | None. The driver never inserts packets. When isolation is off, the mouse simply flows again. |
| Size | Roughly 500 to 700 lines of C on top of the sample. |

### 2.2 User side

`src/mouse_isolation_win.py` exposing the **same** class as the Linux module:

```python
MouseIsolation(on_motion, on_button, on_wheel=None, on_stopped=None, hotkey=True,
               cursor_relay=False)          # Windows extra: True, or a (x, y) -> bool policy
    .start(nodes=None) -> list[dict]        # nodes is accepted and ignored: the filter is class-wide
    .stop(reason="requested")
    .active, .grabbed_devices, .stop_reason
    .status() -> dict                       # Windows extra: the driver's counters through this handle
    .paused, .ticks                         # Windows extras: secure-desktop pause, heartbeat completions
```

Internally it opens the control device, pends reads on a thread, converts `MOUSE_INPUT_DATA` to `(dx, dy)`, buttons, and wheel notches, and fires the same callbacks. Absolute-position packets (`MOUSE_MOVE_ABSOLUTE`: RDP, VM pointers, tablets in mouse mode) are turned into pixel deltas against the previous position. The module also carries the Windows-only helpers the bridge calls around the class: `is_available()` / `MOUSE_ISOLATION_AVAILABLE`, `get_status()`, `list_pointer_devices()` and `stop_all()` for lifecycle, and `inject_button()`, `inject_wheel()`, `cursor_position()`, `set_cursor_position()`, `point_in_window()`, `window_center()`, `hwnd_at_cursor()` and `pointer_speed_multiplier()` for the relay. Two Windows-only additions to the class itself. Both are keyword arguments with defaults, so code written against the Linux signature runs here unchanged. **The reverse is not true and is the direction that matters:** the bridge on this branch calls `MouseIsolation(..., cursor_relay=self._iso_relay_allowed)`, which is a `TypeError` against the Linux class as it stands. Before the merge the Linux constructor has to accept `cursor_relay` and ignore it (it draws the software cursor instead), the same way `start(nodes=...)` is accepted and ignored here. Adding a keyword to one side does not by itself make the two signatures interchangeable.

- **`cursor_relay=True`**, the Windows Full Game Mode model. The reader thread applies every captured motion packet to the real cursor with `SetCursorPos`, scaled by the pointer-speed setting. `SetCursorPos` moves the cursor without creating an input event, so the game's Raw Input, every `WH_MOUSE_LL` hook and every sink registration see nothing, while the window under the cursor gets ordinary `WM_MOUSEMOVE` (measured, parent doc section 8.5). The cursor therefore keeps working on the desktop and on Nimbus, and the game keeps the foreground. Because the reader thread does the moving, a stuck UI thread does not freeze the cursor. Buttons and wheel still arrive only through the callbacks: replaying them with `SendInput` does produce Raw Input, so the bridge decides per event. Over Nimbus's own window it synthesises the Qt press at `QCursor.pos()` (no OS injection, the game sees nothing); anywhere else it calls `inject_button()` / `inject_wheel()`, which is right for the desktop (the click changes the foreground anyway) and for the game's own menus.
- **`hotkey=True`**, the default as on Linux, polls `Ctrl+Alt+F12` with `GetAsyncKeyState` every 100 ms on the reader thread while a read is parked, so it needs no focus and survives a stuck UI thread. The listener in `mouse_hider.py` keeps stopping the pulse.
- **Secure-desktop pause** (no argument; `SECURE_DESKTOP_PAUSE` at module level). On the same 100 ms poll the reader checks whether the desktop that receives input is still its own (`OpenInputDesktop`: the Winlogon desktop behind the lock screen, a UAC prompt and Ctrl+Alt+Del refuses the open, any other desktop has a different name). If not, it turns isolation off, keeps the handle so the device stays Nimbus's, sets `paused` and waits; when the desktop comes back it turns isolation on again and carries on. Without this the physical mouse is dead on a UAC prompt or the lock screen while Game Mode is on: `SetCursorPos` cannot move the secure desktop's cursor, `GetAsyncKeyState` does not see its keys, and the watchdog does not fire because Nimbus keeps reading. Measured with a private desktop (section 5, item 11, B13): off within 40 ms, on again at once after the switch back; and by hand on the real thing: the Windows 11 lock screen itself sits on the Default desktop (the relay keeps working there), the sign-in prompt and UAC prompts pause the client within about 100 ms and it resumes within about 100 ms of their closing.

**Wired into `src/bridge.py` on 2026-09-05** with the Linux branch's names (`MOUSE_ISOLATION_AVAILABLE`, `_IsolationRelay`, `startMouseIsolation` / `stopMouseIsolation`, `mouseIsolationChanged`): Full Game Mode's step 3 starts isolation with the relay policed by `_iso_relay_allowed` (the real cursor never goes over the game unless that spot is also Nimbus, which is the hook's rule applied before the cursor moves rather than after, so games that read the cursor position see nothing either); `_on_iso_button` synthesises the Qt press, the drag moves and the release at the real cursor position while it is over Nimbus's window, and replays them with `SendInput` anywhere else; `stopFullGameMode` releases the mouse first. Full Game Mode also brings the game to the foreground itself, and a cursor found over the game (the game was clicked, or a window moved under it) is parked onto Nimbus's centre so the relay policy never leaves it stuck. The software cursor stays on that branch for the merge, but `_iso_send_mouse` does not: both branches have it, and they differ only in where the position comes from, the Linux one from the software cursor's window coordinates (`_iso_x`, `_iso_y`) and this one from the real `QCursor.pos()`. The QML-facing API that the menu item and the indicator need is already here (`mouseIsolationActive` as a `Property`, `isMouseIsolationAvailable()` and `isMouseIsolationActive()` as slots, and `getGameModeDiagnostics` reporting `mouse_isolation` and `mouse_isolation_active`); only the QML is missing. What to take from the Linux branch's `Main.qml` is the `mouseIsolationItem` menu entry and its `onMouseIsolationChanged` handler. Its `isolationCursor` item is the software cursor and stays Linux-only, since on Windows the real cursor is the indicator. The `WH_MOUSE_LL` hook in `mouse_hider` stays on as well; with the relay policy it only ever sees replayed clicks.

Three things to get right in that merge:

- `MOUSE_ISOLATION_AVAILABLE` in the Windows module is True only when the driver's control device existed at import time (held by another process still counts as installed), so a Windows machine without the driver keeps today's `mouse_hider` Game Mode. The Linux flag is platform-only; do not "simplify" the Windows one back to that, or Game Mode would skip `mouse_hider` on every Windows machine.
- In the Linux branch's `startFullGameMode`, the `mouse_hider` step is an `elif` on the isolation step. On Windows both should run: isolation takes the packets away, and `mouse_hider` still owns the `ClipCursor` release and the `Ctrl+Alt+F12` hotkey. Make them independent `if`s.
- The isolation members either side of the callbacks diverge, though the callbacks themselves are identical. Windows-only: `_iso_game_hwnd`, `_iso_nimbus_hwnd`, `_iso_relay_allowed`, `_iso_park_cursor_if_stuck`, `_iso_cursor_over_nimbus`. Linux-only: `_iso_x` / `_iso_y`, `_iso_set_cursor`, the `isolationCursorMoved` signal with `isolationCursorX` / `isolationCursorY`, the `controller.isolation_cursor_speed` setting and `_x11_session`. `_start_isolation` differs too: the Linux one takes the evdev `nodes` to grab, the Windows one takes none because the filter is class-wide. Keep the argument and ignore it on Windows, which is what `MouseIsolation.start` already does.

`window_utils.py` (WS_EX_NOACTIVATE) stays exactly as it is. The game keeps the foreground, which is the whole point: the pad keeps working and the mouse is gone.

### 2.3 What changes for the user

- One extra driver in the installer, alongside ViGEmBus. Class filters need the mouse devices restarted once (the installer can do that with `pnputil /restart-device`, no reboot).
- Registration detail that is easy to get wrong: on HID-mouse machines the mouse class `UpperFilters` value already contains `mouclass` (mouhid is the function driver; mouclass rides above it as a class filter). Filters attach in list order, first listed closest to the function driver, so `nimbus_moufilter` must be inserted **before** `mouclass` to sit between mouhid and mouclass and receive `IOCTL_INTERNAL_MOUSE_CONNECT`. And `mouclass` must never be removed from that list; the dev scripts refuse to write a list without it.
- Full Game Mode turns isolation on by default (`controller.game_mode_isolate_mouse`); the View menu's "Isolate Mouse" toggle and the status indicator arrive with the Linux branch merge. What the user sees on Windows: the cursor keeps moving and clicking everywhere as before, the game stops turning when the mouse moves, and the game stays in the foreground with its gamepad. `Ctrl+Alt+F12` gives the mouse back at once; so does closing Nimbus, and a frozen Nimbus loses it within 2 s.
- Failure modes to design for: if Nimbus dies while isolated, the mouse comes back within a frame (handle cleanup); if it freezes, within 2 s (heartbeat, interface v3). If the driver itself fails to load, the mouse devices do **not** start, because a class upper filter is mandatory once it is listed in `UpperFilters` (Device Manager Code 39/19; this is the "keyboard and mouse unusable after restart" failure other filter projects warn about). The installer must therefore register the filter, restart the mice, verify the driver is running and every mouse is healthy, and roll the registry entry back automatically if not, with a restore point taken first. The keyboard is never filtered, so manual recovery is always possible from the keyboard; `driver/README.md` lists the recovery steps.

## 3. Signing and the 2026 policy change

- Attestation signing through Partner Center needs the EV certificate that is already held. Attestation-signed drivers load on retail Windows 10 and 11 with Secure Boot on. That is how ViGEmBus ships. The runbook (registration, the CAB rules, submission, verification of what comes back) is in [driver/SIGNING.md](../../driver/SIGNING.md), and `driver/package.ps1` builds and signs the submission CAB. Nothing has been submitted yet.
- The April 2026 "Windows Driver Policy" removes default trust for drivers signed through the deprecated **cross-signed** root program on Windows 11 24H2, 25H2, 26H1 and Server 2025, in evaluation mode first, with an allow list for a limited set of reputable cross-signed drivers. It is not about attestation: an attestation signature chains to a Microsoft CA, and this machine's `ViGEmBus.sys` (Microsoft Windows Hardware Compatibility Publisher, under Microsoft Windows Third Party Component CA 2014) keeps loading.
- What did change is the framing. Microsoft's Driver Signing Options page (updated 2026-03-23) now files attestation under "Attestation signed drivers **for testing scenarios**" and opens with "For testing purposes only". The listed restrictions are still only no retail Windows Update, no Windows Server, and no certification claim; nothing says attestation-signed drivers stop loading, and no end date has been published. Plan for attestation now and treat it as good for this release cycle, not as settled infrastructure. The fallback is WHCP with HLK, a different order of work; Microsoft did expand HLK/DevFund coverage for software and filter drivers in the 26H1 HLK (22 tests to 41), though aimed mostly at file system minifilters. Re-read that blog before assuming a mouse class filter has an HLK path.
- Ship detection of Code Integrity events 3076 (audited) and 3077 (blocked) in the diagnostics dialog, so a user whose driver stopped loading gets a real explanation. The dev machine used for the measurements is itself still in the policy's evaluation mode because another cross-signed driver (`loopbe1.sys`) is audited at every boot; test on a clean Windows 11 VM too.
- Development can use test signing (`bcdedit /set testsigning on`) on the dev machine, where Secure Boot is already off. Preproduction signing from Partner Center is the option when Secure Boot must stay on.

## 5. Test plan

1. `tests/probe_mouse_filter_windows.py` (unattended): status readable, start/stop lifecycle, handle-drop release, watchdog release, exclusive open, and the interface v2 read that fails with `ERROR_NOT_READY` after a watchdog release (U1 to U6). Safe over a remote session; the mouse is isolated for a few seconds at a time with nobody moving it. **Passed 2026-09-05.** Ten robustness checks were added the same evening (U7 to U16, about a minute; `--quick` skips them, `--soak` sets the soak length) and **passed 16/16** on the dev machine, then 16/16 again after the Verifier reboot with Driver Verifier's standard checks and WDF verification on the filter (item 5). They cover what the happy path does not, still with nobody at the mouse:
   - U7 client API edges: availability flags, double start and stop, `DriverBusyError` while another handle is open, `stop_all()`.
   - U8 watchdog timing: with no read ever issued, release landed 2.09 to 2.11 s after `SET_ISOLATION(1)` (2 s timeout, 250 ms period).
   - U9 six reads each parked 0.9 s and then cancelled with `CancelIoEx` kept isolation on for 5.4 s: a read arrival refreshes the watchdog, a cancel does not.
   - U10 a client killed with `TerminateProcess` while a read is parked: the device was free 16 to 31 ms later through handle cleanup, watchdog untouched.
   - U11 a client suspended with `NtSuspendProcess` for 3.5 s. On interface v2 a parked read counted as alive by design, so a hung Nimbus would have held the mouse until killed from the keyboard; that is what motivated v3. With v3, rerun the same evening, the frozen client lost the mouse while still suspended (watchdog release 2 s after its last read) and reported `released by driver watchdog` on resume. A correction: the first run of this check suspended the venv's launcher process instead of the interpreter, so its "kept isolation" result was the design, not a measurement; the check now targets the interpreter by pid.
   - U12 200 client start/stop cycles and 500 raw isolate/release cycles: process handle count unchanged, counters clean.
   - U13 16 threads racing the exclusive open: never two handles at once, no error other than busy.
   - U14 four reads parked on one handle: `CancelIoEx` takes exactly one (995), `SET_ISOLATION(0)` fails the other three (21) at once.
   - U15 19 malformed requests: short and oversized IOCTL buffers, unknown and foreign codes, zero-length and 1, 23 and 256 KB reads, `WriteFile`, read-only and write-only handles, the `\\?\GLOBALROOT\Device` path.    No packets dropped; the desktop cursor froze during the isolated phase and moved normally afterwards.

8. Cursor relay (section 2.2), in three parts. (a) The primitive, unattended: `tests/probe_rawinput_windows.py` scenario `setcursorpos` must show zero `WM_INPUT` at the fake game and at the sink-registered stand-in and zero `WH_MOUSE_LL` events, while `SendInput` in the same run shows the full delta. **Passed 2026-09-05** (parent doc, section 8.5). 11. **Battle test**, unattended: `tests/probe_mouse_filter_stress_windows.py` (about four minutes with the default 120 s soak; `--only B1,B8` picks checks, `--quick` shortens them). It imports the helpers of item 1 and adds storms, floods, process chaos, CPU starvation, a fuzz of every file API the control device can receive, and a soak, all against one invariant: no client, no isolation. Twelve registered checks produce fifteen records, which is where the totals here come from: B2 records B2b separately and B6 records its three priority phases. There is no B10; the ids skip it. **Run 2026-09-06 against the v3 build loaded at boot, 14/14** (nobody at the physical mouse; `packets_passed` stayed 0 all day). Items 1 (17/17) and 10 (8/8) were rerun afterwards with the modified client, and all three passed again (17/17, 14/14, 8/8) once the item 7 rebuild was installed later that afternoon, and once more under Driver Verifier.
    - B1 ten threads on one handle for 8 s: 162,000 `SET_ISOLATION` and `GET_STATUS` calls, 63,600 reads and 3,200 `CancelIoEx`; every completion was `ERROR_NOT_READY` or cancelled, nothing stuck, pass-through afterwards.
    - B2 512 reads parked at once: `SET_ISOLATION(0)` fails all 512 in 3 ms, `CloseHandle` drains all 512 in under 1 ms. B2b, with N reads parked and none re-issued (a frozen client), the release lands at max(2 s, 1 s + N x 250 ms): 2.1 s for N=1, 3.2 s for N=8, 7.4 s for N=24, because the watchdog ticks one parked read per period. Nimbus parks exactly one read, so its bound stays 2.25 s.
    - B3 eight threads opening, isolating, parking and closing for 8 s (2,196 opens, a million busy refusals, half the closes with isolation on and a read parked): never two holders, and a fresh open never found isolation on.
    - B4 thirty clients terminated at random points of their start-up (3 before they had opened the device, 27 with a read parked): device free and pass-through within 48 ms every time, by handle cleanup, never by the watchdog.
    - B5 stall tolerance, with the parked read's age set deliberately (the client re-issues right after each tick): idle = age + stall. 1.80, 1.90 and 1.80 s kept the mouse; 2.40 s lost it. **So the stall a live client survives is 2 s minus the age of its parked read, between about 0.75 s (read ticked at 1.25 s) and 2 s on v3.** The 2 s in the guarantee is the bound on a frozen client's release, not the stall a live one survives. Interface v4, the same evening, set `NIMBUS_MOUFILTER_TICK_MS` to 250 (one watchdog period): the parked read is then at most about 0.5 s old and the floor is 1.5 s, at no cost since the reader already wakes every 100 ms for the hotkey. The check derives its ages from the tick length, so it holds for both.
    - B6 CPU starvation, 40 busy processes on 32 cores for 10 s. At `NORMAL_PRIORITY_CLASS` the client kept the mouse (11 ticks). At `HIGH_PRIORITY_CLASS` a client with a normal-priority reader **lost the mouse to the watchdog 4.8 to 10 s into the burn** with one or two ticks answered. Fixed in the client the same day: the reader thread runs at `THREAD_PRIORITY_TIME_CRITICAL` (`READER_THREAD_PRIORITY` in `src/mouse_isolation_win.py`), and with it the client kept the mouse through the HIGH burn (11 ticks) while the control run with the reader forced back to normal lost it again. Games and launchers at HIGH priority are a real configuration.
    - B7 a client that opens the device inheritably, isolates, hands the handle to a child and dies: the child held the device, the watchdog released 2.1 s after `SET_ISOLATION(1)`, and the device was free once the child exited. The production client's handle is not inheritable (checked).
    - B8 fuzz: 4,000 random control codes over every method and several device types (`FILE_DEVICE_FILE_SYSTEM` ones route through `NtFsControlFile`), 1,240 calls with invalid user pointers, `NtReadFile` with bad buffers and lengths, a read whose buffer was freed while parked, `ReadFileEx` with an APC, every other IRP major (query and set information, volume information, flush, lock, directory, EA, security), 36 open variants (path components after the device name, odd access masks, dispositions and flags, `NtCreateFile` options) and a `DuplicateHandle` storm of 1,000. Every call returned the expected error, nothing succeeded that should not have, nothing hung, the driver stayed healthy. Notable: any path component after the device name opens (the framework accepts every create); DELETE, WRITE_DAC, WRITE_OWNER and SACL access are refused by the SDDL; isolation survives until the last duplicate closes.
    - B9 120 s soak with the production client: 114 ticks (0.95/s), no release, process handles flat. The driver's own pool tag (`nimb`, everything KMDF allocates for it, readable without privilege through `SystemPoolTagInformation`) stood at 38 live allocations, 16 KB, after some 700,000 requests in the session. It is not flat, and the way it moves is the evidence: each 512-deep flood (B2) leaves about 27 more live entries at first, the increments shrink (23, 15, 11, 7, 4) and twelve floods in a row level off at 279 (124 KB), an idle wait changes nothing, and runs with one or two reads in flight bring it back down (212 after the next one, 38 after a couple). That is KMDF's per-device request lookaside, capped at 256 entries above the 38-object baseline, whose depth grows with bursts and is trimmed by the balance set manager, with the trimmed entries returned on the next use; a leak would neither level off nor drain. Nimbus keeps one read in flight. The system-wide nonpaged pool grew by hundreds of MB during the day, but it drifted just as fast with nothing running, and the per-tag view puts it on the filter manager (`FMsc`, `FMsl`), not this driver.
    - B11 six client processes churning open, isolate, park, close for 12 s while one was terminated every 400 ms (29 kills, 1,818 opens): no process, and no open by the monitor, ever found isolation left on.
    - B12 synchronous handles: `CancelSynchronousIo` cancels the read and isolation stays; `CloseHandle` from another thread waits for the blocked read, which the heartbeat completes, so it returns after about 0.75 s (on v2 it would have waited for a mouse packet); `TerminateThread` on the reading thread cancels the read and the watchdog releases 2.1 s later; an overlapped read whose thread exits is cancelled and isolation continues.

    - B13 (added with v4) the input switched to a private desktop for a second, the unattended stand-in for the lock screen and the UAC prompt, which live on the Winlogon desktop a user process cannot switch to: the client turned isolation off 40 ms after the switch, kept the device and stayed active, and turned it on again at once when the desktop came back, with no stop callback and no watchdog release. Before this the physical mouse was dead on a UAC prompt or the lock screen while Game Mode was on: `SetCursorPos` cannot move the secure desktop's cursor, `GetAsyncKeyState` does not see its keys, and the watchdog does not fire because Nimbus keeps reading (section 2.2, secure-desktop pause). **Tried by hand the same evening** with the client isolating on v4 and every transition logged: `LockWorkStation` moved the input off the Default desktop within 64 ms and the client paused 59 ms later; 0.9 s after that the input desktop was Default again *while still locked* (session flag LOCK, foreground a `Windows.UI.Core.CoreWindow`, `SetCursorPos` moving the cursor), so the client resumed. On Windows 11 the lock screen itself lives on the Default desktop and the relay reaches it; only the sign-in prompt is on the Winlogon desktop, and it paused the client again for the 3.3 s it was up, with the resume 64 ms after the unlock. Two UAC prompts from `Start-Process -Verb RunAs` paused isolation 51 and 112 ms after the secure desktop appeared and resumed 109 and 51 ms after it was cancelled. No watchdog release, no stop callback, 873 heartbeat ticks in the 3.8 minutes.

12. **The machine losing the ability to load the driver**, and the guards against it. No probe above catches this, because it is not a property of the code: the filter is registered, correct and previously verified, and the *machine* changes underneath it. A class upper filter is mandatory once listed, so a filter that will not load means Windows starts no mouse device at all. `install-dev.ps1` covers the install (signature, this boot's Code Integrity state, verify, roll back); nothing covered the drift afterwards, and the drift is the dangerous half.

    **It happened on 2026-09-07.** The v4 build had been installed and verified on 2026-09-06. Test signing was off by the evening, so Kernel-PnP logged event 219 `\Driver\nimbus_moufilter failed to load, Status: 0xC0000428` (`STATUS_INVALID_IMAGE_HASH`) at every device start from 18:08 on 2026-09-06, and the machine came up on 2026-09-07 with the mouse at problem code 52 (`CM_PROB_UNSIGNED_DRIVER`), `sc query nimbus_moufilter` STOPPED with win32 exit 1077, and `UpperFilters` still reading `nimbus_moufilter, mouclass`. Two things made it worse than it needed to be. TeamViewer kept working (it injects with `SendInput`, above `mouclass`, as the note below already says), which reads as "the mouse is fine" and is not. And this document's own recovery table told you to run `bcdedit /set testsigning off` and reboot to play an anti-cheat game, without saying that doing so while the filter is registered is exactly how you arrive here. Recovery was the `UpperFilters` edit plus `pnputil /restart-device`, with the mouse back and no reboot needed.

    Four guards were written the same day, three of them new scripts:
    - `driver\check-mouse-filter.ps1`, read-only and unelevated: exits 1 when the filter is registered but would not load in this boot, 2 when the mouse is already broken. It reads test signing from `NtQuerySystemInformation(SystemCodeIntegrityInformation)`, because `Get-AuthenticodeSignature` reports `Valid` off the still-trusted test certificate while Code Integrity refuses the driver anyway, and `bcdedit` reports the setting for the *next* boot.
    - `driver\disable-testsigning.ps1`: detach the filter, then change the setting. The same two steps in the only order that cannot strand you.
    - `driver\recover-mouse.ps1`, the emergency path, self-contained on purpose (no dot-sourcing, no repo layout assumptions) since it runs on a machine that is already broken.
    - `driver\nimbus-mouse-guard.ps1`, registered by `install-dev.ps1` as the `NimbusMouseFilterGuard` task (SYSTEM, at startup and daily), which detaches a registered-but-unloadable filter by itself. The daily trigger is the one that matters: it disarms the trap while the mouse still works. It is deliberately timid, and refuses to act when it cannot read the Code Integrity state, when only some of the mice are broken, or if the write would leave `UpperFilters` without `mouclass`.

    **Verified 2026-09-07** on the recovered machine: all ten `driver\*.ps1` parse; `check-mouse-filter.ps1` reports the recovered state correctly (filter not registered, `CodeIntegrityOptions = 0x1`, one mouse OK, exit 0); the guard runs, logs to `%ProgramData%\ProjectNimbus\logs\mouse-guard.log` and exits without acting when the filter is absent. The decision function was exercised against the real failing configuration by extracting `Test-WouldLoad` from the file through the PowerShell AST and invoking it: against the built `.sys` with the certificate still trusted and test signing off it returns `WouldLoad: False, SigStatus: Valid`, which is the detach decision, and is the case a signature check alone gets wrong. **Not yet run:** the detach path itself and the task firing at boot, both of which need the mouse deliberately broken. Do that on the next driver reinstall, with `install-dev.ps1 -NoGuard` first, then `bcdedit /set testsigning off` and a reboot to confirm the unguarded failure still reproduces, then the guard registered and the same reboot to confirm it repairs it.

**Remote control injects above the filter.** TeamViewer delivers the remote pointer through `SendInput`, so it never touches `mouclass` and the filter neither sees nor blocks it (measured: 72 `WM_MOUSEMOVE` at the game, 0 packets at the driver). The same holds for any tool that injects input in user mode. Hands-on tests need someone at the physical mouse, which is why the attended probe prompts with dialogs.

**Test signing blocks anti-cheat.** EasyAntiCheat, BattlEye and Vanguard refuse to start while `testsigning` is on, so item 3 cannot use Elden Ring on the dev machine. Run it against a non-anti-cheat Raw Input game under test signing, and repeat it with Elden Ring only once the driver is attestation-signed (or on a second machine that loads the signed build). **Turning test signing back off is not a one-liner while the filter is installed**: the dev driver then cannot load, and a registered filter that cannot load means no mouse starts at all (item 12). Use `driver\disable-testsigning.ps1`, which detaches the filter first.

## 7. Explicitly out of scope

- Keyboard filtering of any kind.
- Injecting mouse motion (the desktop cursor is driven by the real mouse whenever isolation is off).
- Per-application filtering. It is not possible at this layer; the parent doc explains why.
- Anything that hides the driver from anti-cheat. Nimbus must be openly identifiable.

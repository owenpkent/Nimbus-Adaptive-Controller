# Second cursors click Nimbus but cannot blind games

No: a second cursor cannot replace the Nimbus Mouse Filter on its own, because the filter does two jobs and a second cursor only does the easy one. Drawing a pointer over the never-focused Nimbus window and delivering clicks to it without activation is solvable in user mode, either with a cursor Nimbus draws itself or with a synthetic pen from `InjectSyntheticPointerInput`. Keeping the physical mouse's motion away from a foreground game is not: Windows has **one system cursor, no multi-pointer API, and no Raw Input flag that makes any process the exclusive receiver of a mouse**, and the mouse collection itself is opened exclusively by the Raw Input Manager, so user mode cannot even read it. The only ways to blind the game are to drop the packets below win32k (a kernel filter, which is what Nimbus has) or to make the physical pointer stop being a Windows mouse at all. The strongest driverless route is the second kind: a roughly **USD 17.50 RP2040 USB-host adapter** that re-enumerates the user's mouse as a vendor-defined HID collection, which no game registers for, which Nimbus reads from user mode without admin rights, and which fails safe (unplug it and the mouse is a mouse again). WinUSB rebinding and UsbDk also work for a dedicated spare USB mouse, and Tobii's SDKs remove the mouse entirely for eye-gaze users. The stakes are sharper than they look: **EAC, BattlEye and Vanguard all refuse to run under test signing**, which the current driver needs, so today the filter cannot be used with most protected online games no matter how well it works. On Linux, keep `EVIOCGRAB`: X11 MPX leaks raw motion to native SDL games, and Wayland multi-seat exists only on wlroots compositors and Weston.

## Raw Input is a broadcast that no user-mode flag can narrow

The reason the WH_MOUSE_LL measurement failed is structural, not a hook quirk. Microsoft recommends WM_INPUT for camera control because it is "read directly from the Human Interface Device (HID) stack" before pointer ballistics, and even DirectInput mouse "creates a second thread to read WM_INPUT data" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/dxtecharts/taking-advantage-of-high-dpi-mouse-movement)). SDL2 relative mode uses Raw Input by default ([SDL2 wiki](https://wiki.libsdl.org/SDL2/SDL_HINT_MOUSE_RELATIVE_MODE_WARP)), Unreal's high-precision mode is raw input ([Epic docs](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/SlateCore/FReply/UseHighPrecisionMouseMovement?lang=en-US)), and shipped engines drain it with `GetRawInputBuffer` ([PH3 blog](https://ph3at.github.io/posts/Windows-Input/)). Newer titles use GameInput, which Microsoft now says to use "for all new code" and which accumulates per-mouse deltas "only for the mouse events that a process receives while it has input focus" ([GameInput overview](https://learn.microsoft.com/en-us/gaming/gdk/docs/features/common/input/overviews/input-overview); [GameInput keyboard and mouse](https://learn.microsoft.com/en-us/gaming/gdk/docs/features/common/input/advanced/input-keyboard-mouse?view=gdk-2510)). Every one of these paths is gated by **focus, not by where the cursor is**, so a cursor parked over a topmost Nimbus window changes nothing while the game stays foreground, and the project has already measured that Elden Ring drops the pad the moment it loses foreground.

Registration cannot fix this from Nimbus's side. Raw input is delivered to every registered process "as long as it has the window focus"; `RIDEV_INPUTSINK` adds a background listener without removing the foreground one; `RIDEV_EXINPUTSINK` fires only when the foreground app is not registered at all; and `RIDEV_NOLEGACY` and `RIDEV_CAPTUREMOUSE` change only the registering application's own messages. The complete flag list contains nothing resembling exclusive ownership ([RAWINPUTDEVICE](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-rawinputdevice)). Per-device selectivity exists only on the receiving side, via `hDevice` ([Raw Input Overview](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-raw-input)), so a game registered for the generic mouse collection gets every mouse. Underneath that, Windows lists the mouse collection (usage page 0x01, usages 0x01-0x02) as **"Exclusive"** and states that the "Raw Input Manager (RIM) opens all such devices exclusively" ([HID Architecture](https://learn.microsoft.com/en-us/windows-hardware/drivers/hid/hid-architecture)), which is why no user-mode app can `ReadFile` a live system mouse either.

| User-mode trick | Raw Input / DirectInput games | WM_MOUSEMOVE / GetCursorPos games | GameInput games |
|---|---|---|---|
| WH_MOUSE_LL returning nonzero | not blocked (project measurement) | blocked | unknown, assume not blocked |
| ClipCursor / SetCursorPos pinning | not affected | defeated | unknown |
| RIDEV_NOLEGACY / CAPTUREMOUSE in Nimbus | affects only Nimbus | affects only Nimbus | no effect |
| SendInput-driven second cursor | adds `hDevice = 0` raw events to the game | moves the one system cursor | unknown |

Existing multi-cursor software confirms the pattern rather than escaping it. Microsoft's MultiPoint Mouse SDK drew up to 25 cursors inside its own WPF window and required its own control because "most of the standard WPF controls do not respond to mouse devices" ([archived MSDN](https://learn.microsoft.com/en-us/previous-versions/msdn10/ff853248(v=msdn.10))), and MultiPoint Services is no longer developed ([Microsoft Learn](https://learn.microsoft.com/en-us/windows-server/get-started/removed-deprecated-features-windows-server)). ManyMouse only reads WM_INPUT ([icculus/manymouse](https://github.com/icculus/manymouse)). MouseMux, the most polished current product, runs "with no drivers" and admits that "games are hit and miss: some work, many do not" ([MouseMux FAQ](https://www.mousemux.com/pages/faq/)). The one tool that truly takes a mouse away from Windows, Pluralinput, does it by installing "its own mouse and keyboard driver for the devices you have selected" and has not been updated since 2017 ([WhatSoftware](https://whatsoftware.com/install-multiple-mouse-and-keyboard-on-one-computer/)). HidHide, the obvious signed candidate, says outright that it "cannot block Raw Input" and cannot treat mice the way it treats gamepads ([HidHide FAQ](https://docs.nefarius.at/projects/HidHide/FAQ/)).

## A synthetic pen can replace the relay, not the filter

The pointer half has a genuinely native answer. `CreateSyntheticPointerDevice` accepts only `PT_TOUCH` or `PT_PEN` (no mouse type) and `InjectSyntheticPointerInput` has shipped since **Windows 10 1809**, with up to 256 touch contacts or one pen per device, positioned in virtual-screen coordinates ([InjectSyntheticPointerInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-injectsyntheticpointerinput); [CreateSyntheticPointerDevice](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-createsyntheticpointerdevice)). The resulting `WM_POINTERDOWN` "targets the window over which the pointer makes contact," and an inactive window receives `WM_POINTERACTIVATE` and may answer `PA_NOACTIVATE` ([WM_POINTERDOWN](https://learn.microsoft.com/en-us/windows/win32/inputmsg/wm-pointerdown); [WM_POINTERACTIVATE](https://learn.microsoft.com/en-us/windows/win32/inputmsg/wm-pointeractivate)). Qt's Windows plugin handles pointer messages natively by default ([QGuiApplication](https://doc.qt.io/qt-6/qguiapplication.html)), and Weylus is a working open-source user of pen injection ([DeepWiki: Weylus](https://deepwiki.com/H-M-H/Weylus/5.4-windows-input)). A pen also has a hover state, which touch lacks in any useful form ([InjectTouchInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-injecttouchinput)). Pen and touch are digitizer usages (page 0x0D), a different collection from the 0x01/0x02 mouse that games register ([HID Architecture](https://learn.microsoft.com/en-us/windows-hardware/drivers/hid/hid-architecture)).

The decisive risk is **mouse promotion**. If a pointer message reaches `DefWindowProc` unrecognized, "DefWindowProc may generate mouse input" ([WM_POINTERDOWN](https://learn.microsoft.com/en-us/windows/win32/inputmsg/wm-pointerdown)), reverse-engineering notes say synthetic-API input is promoted exactly like real pen and touch ([jchv/WmPointerDemo](https://github.com/jchv/WmPointerDemo/blob/master/Syscalls.md)), and a 2012 report from The Witness developers saw promoted touch arrive as WM_INPUT in a raw-input app ([The Witness](http://the-witness.net/news/2012/10/wm_touch-is-totally-bananas/)). No Microsoft document says whether a pen tap on a non-activating Nimbus window moves or hides the system cursor, or whether the foreground game receives a promoted `RIM_TYPEMOUSE` packet. If Qt consumes every pointer message, promotion never happens, which is the good case, but that is a hypothesis to measure. The alternative of steering a second cursor with `SendInput` is strictly worse: injected input goes "through the Win32 cursor pipeline" and lands in the game's raw stream with a null device handle, which is why GameStream and Parsec use kernel or virtual-USB drivers instead ([Apollo issue #1479](https://github.com/ClassicOldSong/Apollo/issues/1479); [RAWINPUTHEADER](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-rawinputheader)).

Even in the best case the pen only replaces the cursor relay. Something still has to steer it, and that something is the physical mouse, whose own packets reach the game unless a lower layer drops them. The realistic value is a hybrid: keep a swallowing layer, and replace "warp the real system cursor into Nimbus" with a synthetic pen, so the game's cursor state is never disturbed and Nimbus receives native pointer events instead of relayed ones. That trims focus and cursor side effects; it does not remove the driver.

## Making the mouse stop being a mouse is the only driverless swallow

Since nothing in user mode can divert a mouse's packets, the non-kernel options all change what the device is. The ranking below weighs isolation strength, the safety of the worst failure, setup burden for a disabled user, and anti-cheat exposure.

| Rank | Approach | Swallows the mouse? | Kernel code | Setup | Coverage | Worst failure |
|---|---|---|---|---|---|---|
| 1 | Vendor-defined HID adapter (RP2040 USB host) | Yes, the game never sees a mouse | None | Buy and flash a board, no admin | Any USB mouse; Bluetooth with an nRF52840 build | Unplug it and the mouse works normally |
| 2 | Tobii SDK for eye-gaze users | Yes, no mouse exists | Vendor runtime only | Tobii tracker, license review | Gaze users only | None for the mouse |
| 3 | WinUSB rebinding (Zadig, or a shipped INF) | Yes | Inbox Microsoft WinUSB; self-signed catalog | Admin per bind, rollback risk | USB only; not Bluetooth or touchpads | That mouse is dead without Nimbus |
| 4 | UsbDk persistent hider | Yes | UsbDk USB hub filter | Admin install | USB only | Hidden until unhidden; hub filter boot risk |
| 5 | Synthetic pen plus the existing filter | No, the filter still does it | The current filter | None extra | All mice | Same as the filter today |

**The vendor-defined adapter is the standout.** Windows attaches the mouse class driver only to usage page 0x01 usages 0x01-0x02, and vendor pages (0xFF00-0xFFFF) are claimed by no inbox client ([HID Architecture](https://learn.microsoft.com/en-us/windows-hardware/drivers/hid/hid-architecture)). Raw input is opt-in per collection and non-mouse devices arrive as `RIM_TYPEHID` ([Raw Input Overview](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-raw-input)), so a game registered for the mouse never receives it, and nothing moves the cursor. User mode reads such a collection with SetupDi, `CreateFile` and `ReadFile` ([Opening HID Collections](https://learn.microsoft.com/en-us/windows-hardware/drivers/hid/opening-hid-collections)), the same way QMK's Raw HID tooling does with hidapi on page 0xFF60 ([QMK docs](https://docs.qmk.fm/features/rawhid)) and the way Chrome's WebHID exposes non-protected collections to unprivileged pages ([Chrome for Developers](https://developer.chrome.com/docs/capabilities/hid)). The Adafruit Feather RP2040 with USB Type A Host costs **USD 17.50** ([Adafruit](https://www.adafruit.com/product/5723)), and jfedor2's open-source HID Remapper already runs on it, already carries a WebHID configuration collection, and has an nRF52840 Bluetooth variant ([hid-remapper](https://github.com/jfedor2/hid-remapper)). The Makers Making Change wheelchair adapter proves the Bluetooth-host-to-USB pattern on cheap hardware for the powerchair population specifically ([Wheelchair-Bluetooth-Adapter](https://github.com/makersmakingchange/Wheelchair-Bluetooth-Adapter)). The catch is that **no firmware ships "mouse in, vendor-only HID out" today**: the device must expose no mouse collection at all in Nimbus mode, because a leftover mouse collection is claimed by Windows and reaches the game. A chord or button to switch back to normal mouse output would cover desktop use. Two edges remain open: GameInput 3.4 (May 2026) lets titles read raw HID reports ([Microsoft Game Dev](https://developer.microsoft.com/en-us/games/articles/2026/05/gameinput-update-now-available/)), though a game would have to choose this unknown device deliberately, and the PIO-based USB host's polling limits against high-rate gaming mice are unmeasured. For Nimbus the integration is small: a reader thread feeding the same software-cursor path that Linux isolation already uses, instead of the Windows cursor relay.

**Accessibility hardware splits by whether it is a mouse.** A Tobii tracker is not a HID mouse, and Tobii Game Integration and Stream Engine hand an app gaze and head-pose streams directly ([Tobii Developer Zone](https://developer.tobii.com/pc-gaming/develop/tobii-game-integration/)), so Nimbus could drive its own cursor from gaze with nothing reaching WM_INPUT, pending a read of the license terms. Camera head mice such as TrackerPro 2 emit ordinary cursor movement ([Spectronics](https://www.spectronics.com.au/product/trackerpro-2)) and inherit the mouse problem, which the adapter solves if they are USB. Devices with a joystick mode (GlassOuse PRO, the open-source Cedar joystick) become shared game controllers that games enumerate ([Rehabmart](https://www.rehabmart.com/product/next-generation-assistive-device-glassouse-pro-head-mouse-and-switch-control-interface-53000.html); [Neil Squire](https://www.neilsquire.ca/openat-joysticks-to-increase-digital-access-for-canadians-with-disabilities/)), and game controllers are "Shared" access ([HID Architecture](https://learn.microsoft.com/en-us/windows-hardware/drivers/hid/hid-architecture)), so the game would see a second pad next to Nimbus's.

**Driver rebinding works but is hostile to users.** Zadig warns that a rebound mouse "will no longer be usable for input in Windows but instead will only work with a custom application," needs admin, installs a self-signed catalog certificate, may be silently rolled back after a reboot or replug, and offers no restore button ([Zadig wiki](https://github.com/pbatard/libwdi/wiki/Zadig); [libwdi issue #8](https://github.com/pbatard/libwdi/issues/8)). UsbDk detaches devices from Windows with "direct and exclusive access" and a persistent hider, is Apache-2.0, and released as recently as March 2025 ([daynix/UsbDk](https://github.com/daynix/UsbDk); [releases](https://github.com/daynix/usbdk/releases)), but it is itself a kernel filter on USB hubs, and its Secure Boot and HVCI status on Windows 11 is unconfirmed. Both cover only USB devices: Bluetooth mice and laptop touchpads never pass through them. Their one real advantage over the current filter is the failure mode: a lost binding kills one USB mouse, while a rejected mouse-class upper filter kills every mouse at boot.

The rejected options fail for concrete reasons. Interception can technically capture and drop a specific mouse, but it is LGPL for non-commercial use only with a paid commercial license ([oblitum/Interception](https://github.com/oblitum/Interception)), has an open 2016 bug where devices stop working until reboot after repeated reconnects ([issue #25](https://github.com/oblitum/Interception/issues/25)), and is blocked by FACEIT, Vanguard and EA Javelin ([issue #170](https://github.com/oblitum/Interception/issues/170); [NoPing](https://noping.com/blog/how-to-fix-battlefield-6-interception-error)). A digitizer-class adapter is opened exclusively by RIM and drives the real pointer, the opposite of the goal. Disabling the device through `pnputil` tears down the whole stack, leaving Nimbus nothing to read ([PnPUtil](https://learn.microsoft.com/en-us/windows-hardware/drivers/devtest/pnputil-command-syntax)). RawAccel shows why a signed input driver survives anti-cheat: it only transforms motion and "has a one-second delay on write" ([RawAccel FAQ](https://github.com/RawAccelOfficial/rawaccel/blob/master/doc/FAQ.md)), so it exposes no packet stream Nimbus could use.

## Test signing, not the filter itself, is what anti-cheat rejects

The anti-cheat picture reframes the whole question. BattlEye "cannot support systems running in test-signing mode" ([BattlEye FAQ](https://www.battleye.com/support/faq/); [Epic Games help](https://www.epicgames.com/help/c-202300000001619/c-202300000001668/failed-to-initialize-battleye-service-windows-test-signing-mode-not-supported-error-a202300000012901)), EAC tells users to disable it ([Facepunch support](https://support.facepunchstudios.com/hc/en-us/articles/214240705-Driver-Signature-Enforcement-has-been-disabled)), and Vanguard checks both test signing and integrity checks ([KeenGamer](https://www.keengamer.com/articles/features/troubleshooting/5-ways-to-fix-the-valorant-vanguard-not-initialized-error-on-windows-pcs/)). Since the Nimbus filter loads only under test signing, **the current driver is structurally incompatible with every BattlEye, EAC and Vanguard title**, independent of anything it does to mouse packets. The project's own Arma 3 recipe, launched through `arma3battleye.exe`, sits squarely in that set. The CLAUDE.md warning that turning test signing off with the filter still registered leaves Windows with no mouse makes this worse: a user who toggles test signing to play a protected game risks losing the pointer entirely.

Production signing changes the category from a structural block to a per-driver negotiation. BattlEye blocks drivers "which contain known security issues that can be exploited by cheats" and bans only for actual cheats, kicking for macro tools ([BattlEye FAQ](https://www.battleye.com/support/faq/)); FACEIT maintains a forbidden-driver list ([FACEIT](https://support.faceit.com/hc/en-us/articles/360014237259--Forbidden-driver-error-message-and-blocked-drivers)); and kernel anti-cheats enumerate loaded drivers ([s4dbrd](https://s4dbrd.github.io/posts/how-kernel-anti-cheats-work/)). A signed mouse-swallowing filter is exactly the profile of Interception, which Vanguard refused even after Riot relaxed its driver blocking in 2020 ([devtrackers.gg](https://devtrackers.gg/valorant/p/d7d37c44-when-this-post-is-1-hours-old-riot-will-release-a-hotfix-to-vanguard-to-stop-vanguard-from-blocking-drivers-in-most-cases)), so expect some titles to flag it. No vendor publishes an accessibility exception. The adapter sidesteps all of this because it loads no driver and presents an unremarkable vendor HID device; that is an inference, not a test. It does not remove the other exposure: ViGEmBus itself appears on Battlefield 6 conflict lists ([Appuals](https://appuals.com/battlefield-6-daemon-tools-virtual-controller-interception-and-autohotkey-errors/)) and on Battlefield V anti-cheat complaints ([EA Forums](https://forums.ea.com/discussions/battlefield-v-en/anticheat-blocking-ds4windows/6847116)), so some titles will reject Nimbus regardless of how the mouse is isolated. VAC and Ricochet have no sourced stance on any of these techniques.

## Linux keeps EVIOCGRAB because MPX leaks and Wayland seats are niche

X11 MPX does give a true second cursor, but its isolation fails on the game type that matters most. The XI2 spec says raw events go "exclusively to all root windows" and that XI 2.1+ clients "receive raw events at all times, even when the device is grabbed by another client" ([XI2proto](https://xorg.freedesktop.org/archive/current/doc/inputproto/XI2proto.txt)). SDL2 and SDL3 both select raw motion on all master devices and forward it in relative mode with no master filter ([SDL3 source](https://github.com/libsdl-org/SDL/blob/main/src/video/x11/SDL_x11xinput2.c); [SDL2 source](https://github.com/libsdl-org/SDL/blob/SDL2/src/video/x11/SDL_x11xinput2.c)), so **a native SDL game would turn its camera whenever the user moves pointer B over Nimbus**. Wine does filter raw motion to its ClientPointer master ([Wine mouse.c](https://github.com/wine-mirror/wine/blob/master/dlls/winex11.drv/mouse.c)), so Proton titles would probably be isolated, but that is one reader's choice, not a guarantee. Around the edges MPX is fragile: Mutter hard-codes master pointer id 2 and ignores the second master ([mutter #367](https://gitlab.gnome.org/GNOME/mutter/-/work_items/367)), a 2026 project found that leaked master pairs silently break keyboard focus after a crash ([trycua/cua #3337](https://github.com/trycua/cua/issues/3337)), and GNOME 50 removed the X11 session outright, so Ubuntu 26.04 cannot log into one ([gHacks](https://www.ghacks.net/2026/03/20/gnome-50-releases-with-x11-session-support-removed-and-wayland/)).

Wayland multi-seat has the right semantics, since each seat's pointer and relative-pointer events go only to the surface that seat focuses, and there is no root-window raw broadcast. It exists in practice only on Weston, Sway and River; GNOME, KDE and Niri do not offer it, GTK does not register new seats at runtime, SDL3's support is partial, and Qt is uninvestigated ([blinry survey](https://blinry.org/multi-seat-wayland/); [SDL PR #12626](https://github.com/libsdl-org/SDL/pull/12626)). Xwayland folds every seat's devices into the single X hierarchy as slaves ([xwayland-input.c](https://github.com/mirror/xserver/blob/master/hw/xwayland/xwayland-input.c)), so Nimbus would have to run as a native Wayland client (`QT_QPA_PLATFORM=wayland`) for the isolation to hold, which means rebuilding its X11-specific focus handling. `EVIOCGRAB` plus the software cursor blocks every reader on every desktop and releases when the file descriptor closes, which beats both. A Sway/River seat mode is at most an optional extra later.

## Seven probes would close the open gaps

The report's weakest claims are the ones nobody has measured, and most can be settled in an afternoon each with tooling the project already has.

| Probe | What it settles | Pass condition |
|---|---|---|
| Synthetic pen onto a `WS_EX_NOACTIVATE` Qt window, with a foreground raw-input logger registered on 0x01/0x02 logging WM_INPUT, `hDevice`, `GetCursorPos` and the foreground HWND | Whether the pen hybrid is viable | No WM_INPUT in the logger, cursor unmoved, foreground unchanged, Nimbus gets press and release |
| RP2040 prototype exposing only a 0xFF00 collection (HID Remapper fork or TinyUSB dual-role) | The adapter's core claim | Cursor never moves; the same logger sees nothing; a standard user opens and reads it via hid.dll or hidapi |
| Adapter through the game harness (`left4dead2 --actuator nimbus`, Elden Ring frame oracle) | End-to-end isolation in real games | Zero camera motion from adapter movement while Nimbus reacts to it |
| Adapter latency and polling against a 1 kHz and an 8 kHz mouse | Whether PIO USB host is fast enough | Report rate and added latency within the tolerance the stick shaping probe needs |
| GameInput sample enumerating devices with the adapter attached, and a GameInput mouse reader under the current filter | Both GameInput unknowns | Adapter absent from mouse enumeration; filter blocks GameInput mouse deltas |
| Arma 3 BattlEye recipe with test signing off, adapter plus ViGEmBus only | Whether the driverless stack clears a real anti-cheat | BattlEye starts and the pad drives the player |
| Linux MPX leak with a uinput virtual mouse as the only slave of a throwaway master, plus an SDL2 relative-mode app | Confirms the raw XI2 leak without touching the real mouse | SDL app receives pointer B's motion (expected), documenting why MPX is rejected |

Two paper checks belong alongside them: whether Microsoft attestation signing accepts an INF-only package binding inbox WinUSB to third-party mouse IDs (which would make rebinding shippable without Zadig), and the Tobii Game Integration and Stream Engine license terms for a non-game accessibility app.

## Conclusion

The useful shift is to stop treating the filter driver as one feature. Its pointer job is already portable, since Nimbus has a software cursor on Linux and Windows offers a native pen channel that may do better than the relay; its swallow job is the only part that needs privilege, and it can move from the kernel into a small, cheap, fail-safe piece of hardware. That relocation fixes the two things the current design cannot: a test-signed driver can never ship to players of BattlEye, EAC or Vanguard titles, and a mouse-class upper filter can leave a disabled user with no pointer at boot, whereas an adapter that is unplugged simply stops mattering.

The practical sequencing follows from that. Build the adapter firmware and the pen probe first, because they decide the architecture; pursue production signing for the filter in parallel as the no-hardware path for users who cannot add a device, knowing it trades a structural anti-cheat block for per-title negotiation rather than eliminating it. On Linux nothing needs to change.

# Third-party tools and drivers for multiple cursors and mouse isolation on Windows

Scope: existing products, projects and signed drivers that give a second cursor or hide a physical mouse from applications, how each works, and whether any can replace Nimbus's own test-signed KMDF mouse-class upper filter (swallow the physical mouse so a foreground game's Raw Input never sees it, hand the packets to Nimbus). Research date 2026-09-25. All fetched content was treated as data.

Framing fact used throughout: Windows opens mouse and keyboard HID top-level collections exclusively. Microsoft's HID architecture page lists usage page 0x0001 usages 0x0001-0x0002 (mouse) and 0x0006-0x0007 (keyboard) as "Exclusive" and says "For security reasons, Raw Input Manager (RIM) opens all such devices exclusively. If RIM opens a device in exclusive mode, the user can still open a HID device interface without requesting read and write permissions and obtain HID device information via HIDClass support routines (HidD_GetXxx)." [Microsoft Learn: HID Architecture](https://learn.microsoft.com/en-us/windows-hardware/drivers/hid/hid-architecture) (page updated 2025-07-18). So a user-mode app cannot read reports from a live system mouse's HID collection, and anything that removes a mouse from the game's Raw Input must act in the kernel (a filter below or at mouclass) or take the device away from the HID/mouse stack entirely.

## 1. Multi-cursor products (MouseMux, TeamPlayer, Pluralinput, ManyMouse, Dual Mouse, Microsoft MultiPoint): how they create extra cursors and whether they block input to other apps

### Takeaway
None of the driverless multi-cursor products stop a game from receiving the physical mouse's Raw Input; they read Raw Input themselves and draw cursors, and MouseMux's own FAQ says games that read the raw stream are "hit and miss". The only one that takes a mouse away from Windows (Pluralinput) does it by installing its own driver on the selected device, is beta, unmaintained since about 2017, and not redistributable, so it is a proof of approach rather than a candidate.

### Cited Findings
- MouseMux: markets itself as running "as a normal Windows application with no drivers and no permanent changes"; each extra mouse/keyboard/pen/touchscreen gets its own cursor; modes are Native (Windows default, all devices drive one cursor), Switched input, and Multiplex (several users in different apps at once). [MouseMux store page](https://store.mousemux.com/) (via search snippet); [MouseMux V2 FAQ](https://www.mousemux.com/v2/faq/)
- MouseMux reads "an input device and builds a generic input event" and can convert any source device type to any target type; it has a "capture device" for input injected by remote desktop programs. [MouseMux V2 FAQ](https://www.mousemux.com/v2/faq/)
- MouseMux on games: "Games are hit and miss: some work, many do not." Programs that "read the raw input stream" (games, CAD, 3D tools) need "Force hardware motion" enabled. Nothing in the FAQ claims it hides one mouse from a game's Raw Input. [MouseMux FAQ](https://www.mousemux.com/pages/faq/)
- MouseMux blocking is at the click-arbitration level: "while one user holds a mouse button down, the others are briefly blocked from clicking"; in Multiplex "once a user clicks into a program they own it". [MouseMux FAQ](https://www.mousemux.com/pages/faq/)
- MouseMux is commercial (license includes one year of updates), current major version is V3, supports Windows 7 through 11 and Server, and ships Windows and Web SDKs that let MouseMux "run in the background and perform various actions via API calls". [MouseMux V2 FAQ](https://www.mousemux.com/v2/faq/); [MouseMux FAQ](https://www.mousemux.com/pages/faq/)
- TeamPlayer is by WunderWorks B.V. (the brief's "DigitalWorks" does not match any source found; "Dicolab TeamPlayer" also appears as a name). It shows one colored cursor per connected mouse; "the company has gone and the product is discontinued", with free old versions (TeamPlayer4 Lite) still circulating on download sites. [WhatSoftware: MouseMux alternatives](https://whatsoftware.com/install-multiple-mouse-and-keyboard-on-one-computer/); [MakeUseOf: TeamPlayer](https://www.makeuseof.com/tag/teamplayer-use-multiple-keyboard-and-mice-on-one-system/); [AlternativeTo: Dicolab TeamPlayer](https://alternativeto.net/software/teamplayer)
- Pluralinput: "Pluralinput installs its own mouse and keyboard driver for the devices you have selected"; the primary mouse keeps the white Windows cursor, added mice get colored cursors; free for personal use, still beta, "has not had any updates since 2017", recommended to keep backups. [WhatSoftware](https://whatsoftware.com/install-multiple-mouse-and-keyboard-on-one-computer/) (via search snippet)
- Pluralinput's own site: "While in Development, Pluralinput is completely free to use" under an EULA; Windows 7 and later; .NET Framework 4.6; "still under development and lacks in features and compatibility with other applications". No driver name or signing information published. [pluralinput.com](https://pluralinput.com/index-old.html)
- ManyMouse (icculus): a small cross-platform library; on Windows XP and later it uses the WM_INPUT / Raw Input API; it does not use DirectInput and parallel DirectInput use "seems to prevent ManyMouse from getting mouse input"; Windows does not send WM_INPUT on unplug so it polls by device handle. It only reads; it does not block. License is zlib per the upstream repo (not re-verified this session). [icculus/manymouse](https://github.com/icculus/manymouse); [ManyMouse page](https://icculus.org/manymouse/)
- Microsoft MultiPoint Mouse SDK: a managed framework supporting up to 25 mice in one application, built for classroom software; it sits over the Raw Input APIs and manages per-device cursor icons and positions inside the app's own window. Documentation now lives under "previous-versions", i.e. retired. [Microsoft Learn: Welcome to MultiPoint Mouse SDK](https://learn.microsoft.com/en-us/previous-versions/msdn10/ee906605(v=msdn.10)); [Wikipedia: Windows MultiPoint Mouse](https://en.wikipedia.org/wiki/Windows_MultiPoint_Mouse)
- Hardware alternative seen in results: jfedor2's "mouse-multiplexer" (two mice, two cursors) is a hardware/firmware project, not a Windows driver. [jfedor2/mouse-multiplexer](https://github.com/jfedor2/mouse-multiplexer)

### Inferences
- Driverless multi-cursor tools (MouseMux, TeamPlayer Lite, ManyMouse, MultiPoint SDK) all consume Raw Input alongside everyone else. Since Raw Input is a broadcast to every registered window, they cannot prevent a game from also receiving the same physical mouse's WM_INPUT. This matches Nimbus's own measurement that a WH_MOUSE_LL hook does not stop WM_INPUT.
- MouseMux's "Force hardware motion" implies it injects synthetic hardware-like motion for the active virtual user, which is the opposite of what Nimbus needs (it adds motion to the game rather than removing it).
- Pluralinput's approach (replace the selected mouse's driver so it is no longer a system mouse, then read it from the app) is the same idea as the WinUSB/UsbDk route in section 3, and confirms it is workable for extra cursors.

### Gaps
- "Dual Mouse": no product with that name was found in searches; could not characterize it.
- MouseMux V3 internals (whether any optional driver exists in V3, anti-cheat interaction, SDK license terms for embedding) are not published; the FAQ is silent on anti-cheat.
- Which exact driver Pluralinput installs (libusb/WinUSB-based or its own KMDF) and its signing status were not found.
- ManyMouse license was not confirmed from a fetched page this session.

## 2. Signed third-party drivers (HidHide, Interception, RawAccel, reWASD, vendor filters): can Nimbus drive one to swallow the mouse and receive the packets?

### Takeaway
No signed third-party driver found does exactly "swallow this mouse for everyone except Nimbus and hand Nimbus the packets" under a license Nimbus can ship. HidHide explicitly cannot hide mice or block Raw Input. Interception can do it technically (it is an upper filter on the keyboard and mouse class stacks with a user-mode capture API) but carries a commercial-license requirement, an old device-count bug that can leave devices dead until reboot, and it is named and blocked by FACEIT, Vanguard and EA Javelin. RawAccel's driver is signed and anti-cheat tolerated precisely because it only transforms motion with a one-second write delay and exposes no packet stream.

### Cited Findings
HidHide (Nefarius)
- HidHide is a kernel-mode filter driver for Windows 10+ with a configuration utility; it can "deny a specific application access to one or more human interface devices, effectively hiding a device from the application", with a whitelist of applications allowed to see hidden devices. [nefarius/HidHide](https://github.com/nefarius/hidhide)
- FAQ on mice/keyboards: "Mouse and Keyboard inputs travel through different means and routes through Windows and HidHide's blocking mechanism can not interfere with those in the same fashion as it does with Joysticks and Gamepads." Also: "HidHide cannot block Raw Input." Filter attaches only to device stacks created after the driver was registered; cloaking is "all or nothing per device". [Nefarius docs: HidHide FAQ](https://docs.nefarius.at/projects/HidHide/FAQ/)
- A redesign would be needed to support mouse/keyboard, and it is a hobby project with no promises (search snippet of the same FAQ); the repo says "There is currently no capacity for any major works on HidHide." License MIT; 1.5k stars. [Nefarius docs FAQ](https://docs.nefarius.at/projects/HidHide/FAQ/); [nefarius/HidHide](https://github.com/nefarius/hidhide)
- Third-party integration exists: control device `\\.\HidHide` / interface GUID `{0C320FF7-BD9B-42B6-BDAF-49FEB9C91649}`, IOCTLs `CTL_CODE(32769, N, METHOD_BUFFERED, FILE_READ_DATA)` with functions 2048-2055 (lists) and 2056-2057 (session blacklist); session entries are removed automatically when the owning process exits. [HidHide DEVELOPER.md](https://raw.githubusercontent.com/nefarius/HidHide/master/DEVELOPER.md)
- Improper removal can "brick" input, so Nefarius publishes a recovery page. [Nefarius docs: Fixing an improper removal of HidHide](https://docs.nefarius.at/projects/HidHide/fixing-a-bricked-system/)

Interception (oblitum / Francisco Lopes)
- Licensing: "Interception is dual-licensed. For non-commercial purposes it adopts LGPL for the library and its source code." Commercial use needs a paid API license or full source license (contact francisco@oblita.com). Built with WDK 7.1.0, "Tested from Windows XP to Windows 10", admin rights to install. 41 commits, 2k stars. [oblitum/Interception](https://github.com/oblitum/Interception)
- Device-count / reconnection bug: after reboot, the 4th keyboard or mouse connection stops transmitting to Windows until reboot; issue opened 2016-03-06, still open, no maintainer fix visible. The widely repeated explanation is that Interception has a fixed limit on device slots and Windows registers a new device on every replug, so KVM switching eventually exhausts it. [Interception issue #25](https://github.com/oblitum/Interception/issues/25); [KeyboardSplitterXbox issue #274](https://github.com/djlastnight/KeyboardSplitterXbox/issues/274) (search snippet)
- Other field failures: mouse and keyboard dead after install and restart, dead after wake from sleep. [Interception issue #117](https://github.com/oblitum/Interception/issues/117); [issue #181](https://github.com/oblitum/Interception/issues/181)
- Anti-cheat: FACEIT rejects "mouse.sys" and the user had to uninstall Interception because the driver is "always in use"; opened 2023-08-14, still open, no maintainer response. [Interception issue #170](https://github.com/oblitum/Interception/issues/170)
- EA Javelin (Battlefield 6) shows an "Interception" incompatible-software error; EA names Interception, AutoHotkey and reWASD as disallowed. [NoPing: BF6 Interception error](https://noping.com/blog/how-to-fix-battlefield-6-interception-error) (search snippet); an aggregator also lists DS4Windows/ViGEmBus, Razer Synapse, Logitech G Hub and Corsair software among BF6 conflicts. [Appuals: BF6 errors](https://appuals.com/battlefield-6-daemon-tools-virtual-controller-interception-and-autohotkey-errors/) (aggregator, not EA primary)
- Vanguard and FACEIT "have taken issue with players who have the Interception driver installed", which is why RawAccel was created as a replacement for the Interception-based InterAccel. [RawAccel repo](https://github.com/RawAccelOfficial/rawaccel) (search snippet)
- HVCI/Memory Integrity blocks drivers "signed with an older cross-signed certificate". [Microsoft Learn: Driver Compatibility with HVCI](https://learn.microsoft.com/en-us/windows-hardware/test/hlk/testref/driver-compatibility-with-device-guard) (via search snippet)

RawAccel
- Windows 10/11 x64 driver that accelerates mouse input "in the raw input stream"; replacement for InterAccel. Releases are signed. [RawAccelOfficial/rawaccel](https://github.com/RawAccelOfficial/rawaccel) (search snippet)
- FAQ: "It is fully signed and has a one-second delay on write, so it cannot be used to cheat and should be considered safe by AntiCheat programs"; reported working with FACEIT, Valorant and Diabotical anti-cheat; settings live in the driver until shutdown and must be rewritten by the GUI or `writer.exe settings.json` after each boot. [RawAccel FAQ](https://github.com/RawAccelOfficial/rawaccel/blob/master/doc/FAQ.md)

reWASD (Disc Soft)
- reWASD's "Unmaps" feature mutes the mouse's native behavior after it is remapped (for example to a right stick), so the cursor stops moving; its help page covers working with a "muted mouse". [reWASD help: How to work with a muted mouse](https://help.rewasd.com/faq/unmappedmouse.html) (search snippet); [reWASD help: Troubleshooting](https://help.rewasd.com/faq/troubleshooting.html)
- reWASD is itself on EA Javelin's disallowed list for Battlefield 6. [NoPing](https://noping.com/blog/how-to-fix-battlefield-6-interception-error) (search snippet)

Reference designs (not products)
- changeofpace/MouHidInputHook filters, modifies and injects mouse packets "into the input data stream of HID USB mouse devices without modifying the mouse device stacks" by hooking mouhid's path into win32k's RawInputThread. [changeofpace/MouHidInputHook](https://github.com/changeofpace/MouHidInputHook)

### Inferences
- HidHide operates on HID collection opens (the path gamepads use: HID/DirectInput/XInput from user mode). A mouse collection is already opened exclusively by RIM and consumed in kernel by mouhid then mouclass, so hiding it from user-mode opens changes nothing for Raw Input. The Nefarius FAQ statement is consistent with this.
- Interception is the only off-the-shelf driver whose API matches Nimbus's need (it can drop a specific device's strokes and deliver them to the capturing process). But: commercial redistribution needs a paid license; its driver was built with WDK 7.1 and is signed under the legacy cross-signing regime, so it likely fails on HVCI/Memory Integrity machines (Windows 11 default on many new installs); it is actively blocked by major anti-cheats; and its device-slot bug reproduces exactly the failure Nimbus wants to avoid (no mouse until reboot). It is a worse risk profile than Nimbus's own filter, not a better one.
- RawAccel's anti-cheat acceptance comes from its design constraints (transform only, one-second write delay, no user-mode packet stream). Driving it to zero sensitivity might stop motion but would not hand motion to Nimbus and would not suppress buttons; it cannot be repurposed without changing the driver, which forfeits its signature. Its signature is the project's, not a redistributable signing service.
- Vendor filter drivers (Logitech G Hub, Razer Synapse, Corsair) are proprietary, have no public API for swallowing and relaying packets, and are themselves on some anti-cheat conflict lists; they are not viable.
- Any mouse-swallowing kernel component Nimbus ships (its own or third-party) will likely be treated by kernel anti-cheats the way Interception and reWASD are. ViGEmBus itself (via DS4Windows) already shows up on BF6 conflict lists per the aggregator, so some titles will reject Nimbus regardless.

### Gaps
- Exact signing status of the current Interception binaries (certificate date, cross-sign, presence on Microsoft's vulnerable driver blocklist) was not found in a primary source.
- The precise Interception device limit (commonly cited as 10 per class, INTERCEPTION_MAX_KEYBOARD / INTERCEPTION_MAX_MOUSE) was not verified from its header this session; issue #25 describes failure at the 4th connection.
- Whether reWASD's mouse mute blocks the mouse's Raw Input for games (as opposed to only the cursor) and what driver implements it were not documented publicly.
- RawAccel's license, filter position (mouclass upper filter is the usual design) and signing route (attestation vs EV) were not stated in the fetched FAQ.
- Wooting: no evidence found of a Wooting mouse-filter driver; Wooting's SDKs target its analog keyboards, so it was not pursued.
- Riot Vanguard's and EAC/BattlEye's stance on HidHide was not found.

## 3. Microsoft-signed or inbox routes: disable or rebind a specific mouse so Windows ignores it and only Nimbus reads it (SetupAPI disable, hid.dll, WinUSB via Zadig/libwdi, libusb, UsbDk, usbipd-win)

### Takeaway
Reading a live system mouse's HID collection from user mode is blocked by design (exclusive RIM open), and disabling the device in SetupAPI removes it from everyone including Nimbus. The route that does work without a custom mouse filter is to take the physical USB mouse off the HID stack entirely: bind WinUSB (Microsoft-signed; INF via libwdi/Zadig) or capture it with UsbDk's hider (Apache-2.0, Daynix, releases through March 2025), then read raw USB interrupt reports from Nimbus via libusb and parse the mouse report. The game then never sees that mouse at all, because Windows no longer has a mouse there. Costs: USB mice only (not Bluetooth, PS/2 or laptop touchpads), per-device report parsing, composite devices need care, and if Nimbus is not running that mouse is dead until the binding is undone.

### Cited Findings
- Mouse and keyboard TLCs are opened exclusively by the Raw Input Manager; other callers may open the interface only without read/write access to query HidD_GetXxx information. [Microsoft Learn: HID Architecture](https://learn.microsoft.com/en-us/windows-hardware/drivers/hid/hid-architecture)
- Zadig can install WinUSB, libusb-win32/libusb0 or libusbK for a device; "if you replace the existing driver for an USB keyboard or mouse, it will no longer be usable for input in Windows but instead will only work with a custom application." After WinUSB is installed the device works with libusb-1.0 based applications. [libwdi wiki: Zadig](https://github.com/pbatard/libwdi/wiki/Zadig)
- Zadig/libwdi generates a .cat and signs it "with a unique self-signed certificate generated on the fly, which is then installed on the current machine". Windows may silently roll back to a higher-ranked driver after reboot or replug; competing INFs can be removed with `pnputil /delete-driver`. [libwdi wiki: Zadig](https://github.com/pbatard/libwdi/wiki/Zadig)
- Zadig historically offered no way to restore HidUsb and could "trash" HID devices; the issues document recovery steps. [libwdi issue #8](https://github.com/pbatard/libwdi/issues/8); [libwdi issue #120](https://github.com/pbatard/libwdi/issues/120)
- UsbDk (Daynix, used by SPICE USB redirection): "provide user mode applications with direct and exclusive access to USB devices by detaching those from Windows PNP manager and device drivers"; Apache-2.0; driver signed with a SHA-256 certificate (Windows 7 x64 needs KB3033929); supports Windows XP onward. [daynix/UsbDk](https://github.com/daynix/UsbDk)
- UsbDk has a persistent hider API: devices hidden this way stay detached until un-hidden or UsbDk is uninstalled. [UsbDkHelperHider.h](https://cgit.freedesktop.org/spice/win32/usbdk/tree/UsbDkHelper/UsbDkHelperHider.h?id=a07a0621674564ecb8c8e195d01e2ae5ffe1ae46) (search snippet)
- UsbDk releases: v1.00-22 (2025-03-17), v1.00-21 (2024-04-30, "add ability to delete all persistent rules"), v1.00-19 (2024-04-20), v1.00-17 (2024-02-26), v1.00-16 (2024-02-02). [daynix/UsbDk releases](https://github.com/daynix/usbdk/releases)
- Signing caveat: a Red Hat KB (RHV) says a spice-usbdk-win build "signed by Red Hat certificate only" did not work on Windows 10 with Secure Boot and USB devices stopped working. This is old and product-specific. [Red Hat solution 3458401](https://access.redhat.com/solutions/3458401) (search snippet; stale)
- libusb's Windows backend supports UsbDk as a backend (patch series introduced it). [libusb-devel: Introduce UsbDk support](https://libusb-devel.narkive.com/AFq31vj3/libusb-patch-0-3-introduce-usbdk-support-for-windows-backend)
- usbipd-win binds a device by swapping in binary copies of VirtualBox's VBoxUSB.sys/VBoxUSBMon.sys; the host loses the device while bound, and in some cases the original driver is not restored on detach (disable/enable in Device Manager fixes it). [DeepWiki: usbipd-win core commands](https://deepwiki.com/dorssel/usbipd-win/4.1-core-commands); [usbipd-win issue #1038](https://github.com/dorssel/usbipd-win/issues/1038); [usbipd-win discussion #902](https://github.com/dorssel/usbipd-win/discussions/902)

### Inferences
- SetupAPI disable (DICS_DISABLE) stops the whole device stack, so the device produces nothing for anyone; it does not leave the mouse readable by one app. Only replacing the function driver (WinUSB/libusbK) or capturing below it (UsbDk) keeps data flowing to a single consumer.
- WinUSB itself is an inbox, Microsoft-signed driver; the only unsigned part of a Zadig install is the generated INF/catalog, which libwdi self-signs and trusts locally. Nimbus could instead ship a proper WinUSB INF catalog through attestation signing, which is a user-mode-only package (no Nimbus kernel binary), a much smaller risk than a mouse-class filter. This needs confirmation of Microsoft's current policy for INF-only attestation submissions (see gaps).
- Failure mode comparison: a WinUSB-bound mouse is dead only while Nimbus is not reading it, and only that one USB mouse; Windows boots with every other pointing device intact. A failed mouse-class upper filter kills every mouse at boot. This is the key safety improvement.
- The user can keep a second pointing device (trackpad, second mouse) as the normal Windows cursor, which matches the "two simultaneous cursors" goal: the rebound mouse becomes a Nimbus-only cursor that Nimbus draws itself (as it already does for its software cursor on Linux).
- UsbDk's hider is attractive because it detaches without changing the device's installed driver (so un-hide restores it cleanly) and is Apache-2.0 redistributable, but it installs a kernel filter on USB hubs, which is itself a kernel driver with its own boot-time risk and anti-cheat visibility.
- usbipd-win is a poor fit (network export, VirtualBox binaries, GPL-licensed components per VirtualBox) and is noted only as proof that detaching a USB HID device from the host is routine.
- Anti-cheat: WinUSB is an inbox driver and loads nothing unusual, so a WinUSB-bound mouse should be invisible to kernel anti-cheat heuristics that target input filters; this is inference, not tested.

### Gaps
- Whether Microsoft attestation signing accepts an INF-only package binding inbox WinUSB to third-party mouse VID/PIDs (and whether Windows Update would later replace it with HidUsb) was not researched.
- Whether current UsbDk release binaries are Microsoft attestation-signed (loads with Secure Boot and HVCI on Windows 11) could not be confirmed from the releases page.
- Wireless receivers (Logitech Unifying/Bolt, other 2.4 GHz dongles) are composite USB devices; binding WinUSB to the whole device vs one interface, and whether vendor pairing protocols interfere, was not researched. Bluetooth mice cannot use this route at all.
- No source was found describing a supported user-mode way to read a mouse collection while mouhid holds it; Microsoft's documentation indicates there is none.

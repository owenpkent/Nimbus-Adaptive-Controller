# Nimbus Adaptive Controller

Free, open-source modular virtual controller for Windows. Turns mouse/GUI input into vJoy (DirectInput) or ViGEm (Xbox 360 XInput) joystick output. Accessibility-first software alternative to the Xbox Adaptive Controller. Python core plus a Qt Quick (PySide6/QML) UI.

## Key rules
- The QML UI talks to Python only through `ControllerBridge` (src/bridge.py), the single QObject exposed to QML as context property `controller` (config as `config`). QML to Python is `@Slot` methods; Python to QML is Signals. Apply sensitivity curves, deadzones, and smoothing inside the bridge before forwarding to a driver interface, never in QML or the interfaces. Custom-layout widgets send raw geometry (`setStickInput`, `setAxisInput`) and the bridge resolves their shaping settings from the profile by widget id (`_reload_widget_shaping`, `_widget_params`); the formula itself is `shape_magnitude` / `shape_vector` in src/config.py and the dialog's curve preview asks the bridge for its points (`shapeCurve`) rather than copying it.
- Two controller backends must stay behavior-compatible: `VJoyInterface` (8 axes X,Y,Z,RX,RY,RZ,SL0,SL1; 128 buttons) and `ViGEmInterface` (4 axes + 2 triggers; 14 buttons). The bridge selects one per profile `layout_type`. When adding or changing a `set_axis`/`set_button`-style method, mirror it in both and honor each backend's hard limits.
- On Linux, `UInputJoystickInterface` and `UInputXboxInterface` (src/uinput_interface.py, pure-Python `/dev/uinput` ioctls) stand in for vJoy and ViGEm with the same method names; the bridge picks them via `_create_joystick_interface()` / `_create_xbox_interface()` and `XBOX_OUTPUT_AVAILABLE`. Any interface method change must be mirrored there too. The joystick device is capped at 56 buttons (evdev limit) and only the active device is kept alive on Linux.
- Custom layouts are a three-way contract: profile JSON `custom_layout.widgets[]`, the rendering in `qml/layouts/CustomLayout.qml` + `qml/components/DraggableWidget.qml`, and the bridge mapping. Adding a widget `type` or field means updating all three (plus `profiles/adaptive_platform_2.json` if it is a default).
- Windows/driver-specific modules (vigem_interface, window_utils, borderless, mouse_hider) and the Linux-only uinput_interface are imported under try/except into `*_AVAILABLE` flags. Keep that graceful-degradation pattern so the app still starts with the driver missing or on another OS.
- Controller mode has two implementations: `mouse_hider.py` on Windows (pulse + Win32 hooks) and `controller_pulse.py` everywhere else (pulse only, driven through the interface API). The bridge switches on `_USE_MOUSE_HIDER`; keep the burst/pulse parameters in sync if you tune one. The pulse must never author a stick position: it emits through `emit_left_stick_transient` / `pulse_left_stick`, which leave `current_values` alone, so a restore re-emits what the user commands rather than what the pulse last read. Game Focus Mode is `WS_EX_NOACTIVATE` on Windows and `Qt.WindowDoesNotAcceptFocus` on X11 (`_apply_no_focus_flag`). Always on Top is `Qt.WindowStaysOnTopHint` (`_apply_always_on_top`); Game Mode pins the window for the session and only unpins what it pinned itself. Both flag helpers must keep restoring the window geometry, because changing a flag can make the xcb plugin recreate the native window.
- Mouse isolation has one bridge API and two implementations, selected by platform at import: `src/mouse_isolation_win.py` (the Nimbus Mouse Filter driver plus the cursor relay; `MOUSE_ISOLATION_AVAILABLE` is True only when the driver's control device exists, so a machine without it keeps mouse_hider Game Mode) and `src/mouse_isolation.py` (`EVIOCGRAB` plus a software cursor). The two `MouseIsolation` classes must keep the same constructor, `start`/`stop` and callback signatures, so every call site in `bridge.py` stays platform-independent. Callbacks run on a reader thread; only the bridge's `_IsolationRelay` queued signals may touch Qt. On Linux, never grab a device that carries keyboard keys unless the uinput pass-through keyboard was created, never grab a pointer whose motion the reader cannot translate (`pointer_support` declines absolute devices, because an exclusive grab on a touchpad strands the user with no pointer), and keep every stop path (toggle, hotkey, `stop_all`, atexit) releasing the grab. Test with a virtual device, not the user's mouse.
- The two isolation implementations live in one class, so they must not share method names. Each entry point is a dispatcher choosing on `_ISO_CURSOR_RELAY`, and the bodies are suffixed `_relay` and `_sw`. Nothing outside that block may call a suffixed method directly. This is not style: Python binds the later definition of a duplicated name, silently, and a merge that defined both sets made the Windows relay dead code while every test still passed. `tests/test_bridge_no_duplicate_methods.py` parses the file (importing it would only see the winners) and fails on any new duplicate; its `KNOWN` list is empty and adding to it needs a reason.
- `driver/nimbus_moufilter/nimbus_moufilter_ioctl.h` and the constants at the top of `src/mouse_isolation_win.py` are one contract (device name, IOCTL codes, status struct, `MOUSE_INPUT_DATA` packing). Change them together and bump `NIMBUS_MOUFILTER_INTERFACE_VERSION`.
- Output backends are built by `ControllerOutput` from injected factories, and the bridge picks them once at construction: uinput on Linux, vJoy/ViGEm on Windows. Everything downstream asks `self._output`, so do not reintroduce per-platform interface construction in the bridge. On Linux only the active back end is kept alive (`_retire_inactive_interface`), because each uinput device is a separate gamepad games can see.
- Linux: the gamepad path is a `uinput` virtual pad and is verified end to end (raw evdev, SDL2, the browser Gamepad API, mouse input through the real QML widgets, and a live Steam/Proton game), so Xbox/Adaptive/Custom profiles work there from source. `pyvjoy` has no Linux equivalent, so `VJoyInterface` stays in permanent simulation mode there and flight-sim profiles have no real output until a Linux vJoy replacement lands. `pyvjoy` also raises `SystemExit` (not `ImportError`) when its DLL will not load, so its import guard must catch `SystemExit` too, not just `Exception`/`ImportError`. See [`docs/setup/INSTALLATION.md`](docs/setup/INSTALLATION.md#linux-installation) for setup and known gaps (Borderless Gaming/Game Focus Mode are correctly gated to Win32; the Game Mode ribbon button is not yet gated and is a dead button on Linux).
- Telemetry stays opt-in only, no PII, hashed identifiers, local-first (src/telemetry.py, src/cloud_client.py, keyring for secrets). Do not add default-on collection or log identifying data.
- `controller_config.json` is generated per-machine and is gitignored, so never commit it. Bundled default profiles live in `profiles/`; user profiles live in `%APPDATA%/ProjectNimbus/profiles/`. The internal app/data-dir name is `ProjectNimbus` (config.py `APP_NAME`), so do not rename it.
- Do not add features to non-primary shells: `src/legacy/` (pygame) and `src/qt_main.py` + `src/qt_widgets.py` (Qt Widgets) are reference-only and not at feature parity. The QML app is the one true UI.

## Stack & layout
- Python 3.8+ with PySide6 (Qt Quick/QML), pyvjoy, numpy, PyInstaller. Xbox 360 output reaches ViGEmBus through `src/padbus_client.py`, a pure-ctypes client for the bus protocol (no `vgamepad`, no client DLL); its `X360Pad` keeps vgamepad's method names on purpose, `BUS_INTERFACES` lists the device interface GUIDs to probe so a Nimbus-owned bus is one more entry, and `PADBUS_AVAILABLE` is True only when a bus device is present. The plan it comes from is `docs/vision/PAD_BUS_FORK_PLAN.md`.
- `src/` Python core: bridge, config, vjoy_interface, vigem_interface, borderless, window_utils, mouse_hider, mouse_isolation_win, telemetry, cloud_client.
- `qml/` UI: `Main.qml`, `layouts/`, `components/`.
- `profiles/` bundled default profile JSON. `build_tools/` PyInstaller packaging. `tests/` vJoy hardware diagnostics and the Windows input probes. `docs/` architecture and dev notes.
- `vm/` the guest VM track of `docs/vision/VIRTUAL_MACHINE_FEASIBILITY.md` (a Windows 11 guest on the Windows host sharing the GPU through Hyper-V GPU-PV, the pad in through Moonlight and Sunshine, the isolation proof as Gate C). Research tooling only, never part of the app or the installer, and Nimbus does not manage VMs. `vm/README.md` is the runbook; the numbered scripts refuse to run out of order. Since 2026-09-13 Hyper-V is enabled on the dev machine (the driver baseline every filter number was measured on has therefore moved; re-run the filter suites before trusting a new driver number) and the guest `NimbusGuest` exists with the GPU partition attached and Sunshine paired with the host's Moonlight; Gates A, B and C passed and Gate D's latency axis was measured (the guest costs two to five frames at the median against one natively; the game and second-machine comparisons are unrun), so the document's conclusion stands: research, not a product. Safe to run unasked: `00-host-preflight.ps1`, `20-check-gpu-partition.ps1`, `30-fetch-iso.ps1`, `guest/render_check.py`, PowerShell Direct reads of the guest (`Get-GuestCredential` in `vm/common.ps1`), the Gate C pair in loopback (`gate_c_host.py --guest 127.0.0.1 --loopback` against `guest/gate_c_monitor.py`), and Gate C against the guest with `--viewer-title Moonlight`, which synthesizes host mouse and keyboard input the way the game harness does, so it is unattended-only. `gate_d_latency.py` with `guest/beacon.py` (Gate D's latency axis) flashes a window on the host's screen for the length of a run: only when nobody is looking at that screen, and never near someone photosensitive; Owen saw it flashing on 2026-09-13. Steps 10, 40 and 50 are elevated (Owen runs them one line at a time), and anything that creates, deletes or re-attaches the guest, or disables Hyper-V, is a "when to ask" item. The guest gets Direct3D 11 and OpenGL, so Gate D runs Left 4 Dead 2 or Half-Life 2, not Elden Ring. Moonlight forwards every host gamepad (the vJoy device becomes guest player 0), and Windows turns a pad into `VK_GAMEPAD_*` key events inside the guest; the monitor counts those apart.
- `netpad/` the network pad prototype of `docs/vision/SEPARATE_GAME_MACHINE.md` section 3.2 (the game on another computer, the pad sent over the LAN to a receiver that creates a ViGEm or uinput Xbox pad). Research tooling like `vm/`: nothing in `src/` imports it and it is not in the installer. Its contract (60 Hz keepalive, neutral after 150 ms, pad destroyed after 2 s idle, 500 packets/s cap, shared key file with HMAC, one live session, neutral first state on resume) was decided by Owen on 2026-09-14 and lives as constants at the top of `netpad/protocol.py`; changing any of them, or wiring it into the bridge, is a "when to ask" item. Test with `python -m tests.test_netpad` (fast suite) and, end to end, `netpad\deploy-guest.ps1 -StartVm` then `python -m netpad.e2e_check --receiver <guest ip>`, which synthesizes no host input and flashes nothing, so it is safe to run unasked.
- `driver/` the Nimbus Mouse Filter (KMDF, Windows only). Built with `driver\build.ps1`, which needs Visual Studio 2022 with the WDK component and WDK 10.0.26100; it is not part of `run.py` or the installer yet. Loading it needs test signing (see `driver/README.md`). Never install or load a kernel driver on someone's machine without asking. Once the filter is registered as a mouse-class upper filter it is mandatory: anything that stops Code Integrity accepting the test-signed `.sys` (a Windows update, `bcdedit /set testsigning off`, Secure Boot back on) means Windows starts **no mouse at all**, and a working TeamViewer cursor hides it because `SendInput` never touches `mouclass`. So never turn test signing off while it is installed; use `driver\disable-testsigning.ps1`, which detaches first. `driver\check-mouse-filter.ps1` (read-only, no elevation) says whether the mouse would survive the next reboot, and elevated `driver\recover-mouse.ps1` gets it back with no reboot. This happened on 2026-09-07; see `driver/README.md` and section 5 item 12 of the plan doc.

## Build, run, test
- Run: `python run.py` on Windows or `./run.sh` on Linux (auto-creates `venv/`, installs requirements, launches `src.qt_qml_app`). Modules run as packages, so keep `src.`-qualified or relative imports. Linux needs write access to `/dev/uinput` (docs/setup/LINUX.md).
- Deps: `pip install -r requirements.txt`.
- Package: follow `build_tools/BUILD_EXECUTABLE.md` (PyInstaller via `build_tools/Nimbus-Adaptive-Controller.spec`).
- Tests: `python tests/run_fast_tests.py` runs the fast, hardware-free suite (the `tests/test_*.py` files, seconds, no driver), and it is what CI runs (`.github/workflows/fast-tests.yml`, `windows-latest`, `QT_QPA_PLATFORM=offscreen`, `requirements.txt` without `pyinstaller`). The files import the app as `src.<module>`, so run one on its own **as a module from the repo root** (`python -m tests.test_bridge_services`), never by path. `test_vjoy.py`, `test_uinput.py` and `test_dialog.py` match the pattern and are skipped by name or self-skip off their platform. pytest is not a dependency. `tests/test_frame_motion.py` covers `tests/frame_motion.py`, the frame motion measurement the game harness uses, with synthetic pictures. The plan behind all of this, and what it found, is `docs/vision/TESTING_STRATEGY.md`.
- Bus client changes: run `tests/test_padbus_client.py` (pure Python, the protocol constants and packing) and `tests/probe_padbus_windows.py` (the real ViGEmBus, about 30 s: plug, XInput read-back, handle-death unplug, replug storm, timing) after any change to `src/padbus_client.py`, then the shaping probe below, since its expected values only hold if the client's float conversion is unchanged.
- Stick shaping changes: run `tests/test_stick_shaping.py` (pure Python, no hardware) and `tests/probe_stick_shaping_windows.py` (the real app, needs ViGEmBus, about 40 s, safe over TeamViewer) after any change to `shape_*` in src/config.py, `setStickInput` / `setAxisInput` in the bridge, the stick paths in `DraggableWidget.qml`, or the widget config dialog in `CustomLayout.qml`; the probe's expected values come from the bridge's own resolved parameters. `tests/probe_game_deadzone_windows.py` measures a game's real stick deadzone and must be started before the game launches. The plan and the results log are in `docs/vision/AIM_ASSISTANCE.md`, sections 12 and 14.
- Real-game tests: `tests/probe_game_harness_windows.py --game left4dead2 --actuator pad` (calibrates the game through its console, about four minutes, unattended, launches and quits the game itself; `--write-calibration` refreshes `src/spectator/calibrations/left4dead2.json`) and `--actuator nimbus` (the real app end to end, then the Spectator+ primitives), and `--actuator netpad` (the pad through the `netpad/` sender and a receiver process over UDP loopback: every pad check plus the NP checks, including that Left 4 Dead 2 never reads a pad the receiver destroyed and re-created). Recipes are `tests/games/*.json` (`halflife2` is the second Source game; `eldenring`, `powerwashsimulator` and `halowars` use the frame-differencing oracle and a `ready_sequence`, PowerWash's menus need the `pointer` step because A there clicks a virtual pointer the left stick moves rather than a highlight, and Halo Wars is the RTS whose sticks drive a camera, whose menus need buttons the bundled profile draws no widget for, and whose timed sequence cannot use `press_until_control` because its title screen animates); the machinery is `tests/game_harness.py`; the plan and the results log are `docs/vision/GAME_TEST_HARNESS.md`. `arma3` (BattlEye, launched by its `exe` key through `arma3battleye.exe`) and `arma3_nobe` (the control) use the `arma3` oracle: a generated mission whose script publishes the pose through the clipboard and takes reset and `NIMBUS_EXEC` script commands back from it, so a copy or paste during a run breaks a read, the pad must be enabled in the player's profile (the oracle does it, behind a backup), the window is applied at readiness only, and nothing presses Start (it freezes the mission's script). Run one at a time so each session's pad is player one. Rerun both after any change to `src/spectator/`, `ControllerBridge.get_spectator`, or the calibration. **Leave the mouse and keyboard alone while one runs**: these games read the mouse for look and the harness foregrounds the game window for each step, so a hand on the mouse turns the camera inside the measurement and nothing can tell it from the pad. Unattended means it needs no help, not that the machine is free. For the same reason the runner never asserts the foreground between the two pose reads of a delta (`front()` warps the cursor). Half-Life 2 needs `--cal-mags 0.4,0.6` when writing its calibration, because its full-deflection turn folds past 180 degrees between pose samples. Recipes may also carry `window` (the harness sizes the game with `src/borderless.py` and records whether it took), `motion` (`{"kind": "rotate"}` for a camera that swings rather than pans, Halo Wars), `reset_buttons` (a reset for a game with no console, checked against a reference frame) and `expect` (bands on the rates a check measured last time, so a run fails when the game's answer changes; `--write-expect` fills them from a good run). Frame verdicts come from `tests/frame_motion.py` (phase correlation and a change grid, never a bare changed-sample count) with thresholds from `--idle-samples` idle seconds.
- Driver changes: run `tests/probe_mouse_filter_windows.py` and `tests/probe_mouse_filter_stress_windows.py` (the battle test, about four minutes, unattended, needs the filter installed) after any change to `driver/` or `src/mouse_isolation_win.py`, and WDK Code Analysis plus CodeQL before a driver commit. The commands and the results log live in `docs/vision/WINDOWS_MOUSE_FILTER_PLAN.md`, section 5.
- VM tooling changes: `python -m tests.test_vm_gate_c` (in the fast suite; the host driver's verdicts against a fake guest with planted faults, and the monitor's bookkeeping) after any change to `vm/gate_c_host.py` or `vm/guest/gate_c_monitor.py`, then the loopback run above. The PowerShell steps have no test beyond parsing; re-read `vm/README.md` and the feasibility document's section 10 before changing them, and keep the versions pinned in `vm/guest/setup.ps1` in step with the README.
- Bridge changes: run `python -m tests.test_bridge_isolation` (the isolation path: platform dispatch checked by running it, delivery to the main window and to a modal dialog, the software cursor) and `python -m tests.test_bridge_no_duplicate_methods` (no method defined twice). Both are in the fast suite; neither needs hardware.
- Linux input changes: run `python -m tests.test_linux_input_safety` (pure Python, runs anywhere, covers the pulse-versus-release race and the absolute-pointer refusal). On an actual Linux box run `./tests/run_linux_validation.sh`, which sets up the venv, records the environment, runs the fast suite plus `tests/probe_linux_stack.py` (the uinput and evdev claims against a real kernel), `tests/test_uinput.py`, `tests/probe_evdev_grab.py` and `tests/probe_always_on_top.py`, and tees one log to paste back. It never grabs the mouse you are holding unless you pass `--grab`.

## Conventions
- PEP 8, type hints, and numpy-style docstrings on public classes and methods (match src/bridge.py). No linter or formatter is configured, so keep the existing style and avoid ruff/black reformatting churn.
- Keep vJoy axis names uppercase (X, Y, Z, RX, RY, RZ, SL0, SL1); button IDs are 1-based.

## When to ask
- Changing the profile / `custom_layout` JSON schema or the `controller_config.json` shape (needs migration plus all three layers updated).
- Changing telemetry scope, cloud endpoints, or credential handling.
- Touching a driver interface in a way that could inject unintended input, or changing failsafe / rate-limit behavior.
- Running any `vm/` step past the preflight on the dev machine: enabling Hyper-V (elevated, a reboot, and the driver baseline changes), creating or deleting the guest, attaching the GPU partition, or installing Moonlight on the host.
